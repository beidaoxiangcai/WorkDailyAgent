## BUG-20260827-01：系统空闲时间重复统计

### 基本信息

| 项目 | 内容 |
|------|------|
| 发现日期 | 2026-08-27 |
| 状态 | 已修复 |
| 影响分支 | `feature/activity-analysis-page` |
| 问题类型 | 采集状态错误、历史数据重叠、统计错误 |

### 问题表现

- 应用使用占比的“系统空闲”明细中出现多条从当天 `00:00` 开始、结束时间不同的记录。
- 同一天的系统空闲累计时长超过 24 小时，例如显示约 `53h 49min`，占比约 `91.56%`。
- 行动轨迹中同一时间范围可能出现重叠的空闲区块。
- 数据库中存在开始时间相同、结束时间逐渐延长的嵌套空闲记录。

本次排查到的直接样本为数据库事件 `10182` 至 `10185`：它们的原始开始时间均为 `2026-08-26 22:31:06`，结束时间分别为次日 `11:04:05`、`12:30:24`、`13:04:50` 和 `13:21:44`。查询 2026-08-27 时，跨天裁剪将这四条记录的展示起点都调整为当天 `00:00`。

### 触发条件

1. macOS 显示器进入休眠，采集器根据“当前时间减去系统空闲秒数”反推最后活动时间。
2. 显示器恢复后，采集器生成一条从最后活动时间到恢复时间的系统空闲事件。
3. 显示器再次休眠和恢复，但期间没有被系统 API 识别到新的键盘或鼠标输入。
4. 系统返回的最后活动时间保持不变，采集器再次从同一个旧起点生成更长的空闲事件。

### 根因

- 合并引擎没有维护“已经统计到哪个时间点”的单调时间水位，每次进入空闲都直接采用系统反推的最后活动时间。
- 应用重启时没有从数据库恢复已记录时间水位，存在重新补录已覆盖区间的可能。
- SQLite 写入层没有检查新空闲事件是否与已有空闲区间重叠。
- 公共查询层只做跨天裁剪和精确事件去重，无法消除开始或结束时间不同的嵌套区间。
- 前端聚合按每条事件的 `duration_ms` 直接求和，因此所有重叠时长都会被重复计入。

### 影响范围

| 模块 | 影响 |
|------|------|
| 系统空闲数据 | 同一段空闲时间重复落库，累计时长可能超过实际经过时间 |
| 活动分析页面 | 空闲时长过大，空闲占比错误，其他应用占比被压低，轨迹可能重叠 |
| 原时间轴页面 | 使用相同查询结果，可能展示重复或重叠的空闲事件 |
| 日报生成 | 使用相同事件查询入口，生成内容时可能读取重复空闲事件 |
| 历史数据 | 错误记录已经持久化，应用重启后仍然存在 |

该问题直接重复生成的是系统空闲事件。普通应用自身的累计时长不会被这条空闲生成逻辑直接重复，但其占比会因统计分母被放大而错误。

排查时在现有数据库的 2026-08-03、2026-08-14、2026-08-16、2026-08-26 和 2026-08-27 数据中发现过相互重叠的系统空闲区间。

### 修复方式

1. 合并引擎增加单调递增的已记录时间水位。
2. 新空闲事件的开始时间取“系统反推的最后活动时间”和“已记录水位”中的较大值，禁止回溯覆盖已经统计的时间。
3. 应用启动时从 SQLite 获取最新已记录时间并恢复水位。
4. 暂停、恢复、黑名单边界和退出时推进水位，避免把不采集的间隔补记为空闲。
5. 存储层写入空闲事件前查询已有空闲区间，只保存尚未被覆盖的时间片段。
6. 公共查询层合并重叠或相邻的历史空闲区间。
7. 历史空闲区间与普通应用事件重叠时，以普通应用事件为准，从空闲区间中扣除重叠部分。
8. 原时间轴、活动分析页面和日报生成共用归一化后的查询结果，保证统计口径一致。

### 历史数据处理

- 不直接删除或改写现有 SQLite 事件，避免破坏历史记录和已保存日报中的事件引用。
- 查询时动态归一化历史空闲区间，现有页面和后续日报使用修正后的数据。
- 已经生成并保存的历史日报不会自动重新生成。

以发现问题时的 2026-08-27 数据为例，数据库直接累计的系统空闲约为 `53.82h`；合并重复区间后约为 `16.97h`，重复计算约 `36.85h`。
